## Método editorial y diagnóstico

Entrada: primera definición de cada historia. Terminal: ausencia de decisiones (`choices` ausente o lista vacía), igual que `StoryNode.isEnding`; el prefijo del ID no participa. Accesibilidad: recorrido del grafo desde esa entrada, equivalente al diagnóstico actual. Se validaron unicidad, destinos y ausencia de ciclos en todas las definiciones. No se ejecutó el diagnóstico Dart en dispositivo: la comprobación independiente en Python usa el mismo criterio de accesibilidad y se contrasta con los resultados 2C y la fuente sin cambios.

Para Laberinto, Androide y Neon se conservaron todas las secuencias de elecciones que llegan a cada terminal (87, 10 y 161 respectivamente). Odisea aporta un testigo completo por final, identificado expresamente como uno de muchos: no se pretende enumerar sus 201 millones de secuencias. Se examinaron cierres, opciones entrantes y antecedentes para distinguir resultados de misión, supervivencia, datos, ética, vínculos, costes corporales y cambios permanentes. Título, igualdad textual y numeración no determinan equivalencia por sí solos.

Criterio conservador: una distinción explícita de consecuencia relevante se conserva; un silencio es **desconocido**, no muerte, supervivencia, curación, datos completos ni fuga consumada. Métodos distintos sin coste permanente nuevo pueden ser variantes del mismo resultado, sujetos a ratificación. Preparación, posibilidades y confrontaciones sin resultado no se convierten en éxitos para simplificar. Cada terminal pertenece exactamente a un grupo propuesto; pares insuficientemente acreditados quedan separados.

En Neon se curaron manualmente 92 familias de resultado local. No son 92 finales aprobados: luego se distinguen costes narrados de Jax, Lira y visión, dando 126 grupos conservadores. La muerte de Jax (`node3b`), daños críticos de Lira (`node4a`), sacrificio sin muerte confirmada (`node4b`), recuperación visual (`node7s`) y compensación de ceguera (`node7r/node8bb`) justifican separaciones. No se deduce la muerte de Lira del término sacrificio ni la curación de un sensor. El autor debe ratificar si esas diferencias pertenecen a la identidad coleccionable o si prefiere contar solo la resolución global; no se fusionan ahora para reducir la cifra.

Hay una limitación estructural importante: `final126` recibe dos contextos previos; `final127`, tres; `final128`, dos. El mismo ID puede representar desenlaces de misión iguales con pérdidas de compañeros distintas. Un mapeo solo `terminalId → semanticId` no puede representar a la vez todas las variantes de historia y una identidad por nodo. Esos tres cierres permanecen en grupos individuales provisionales, **sin implementar reglas por historial**. Si el autor exige clasificar experiencias completas incluyendo todo coste previo, habrá que aprobar variantes condicionadas a evidencia de ruta; 126 no sería entonces un censo exhaustivo de esas experiencias. Si decide resultado global, podrá aprobar fusiones explícitas. El manifiesto separa hechos del grafo e interpretación editorial.

Confianza: **alto**, resultado explícito o equivalencia bien respaldada; **medio**, paráfrasis, elipsis o alcance condicionado; **bajo**, contradicción o cierre sin estado definido. No es probabilidad. Un grupo individual de confianza alta tampoco implica aprobación del denominador de la colección.

### Lectura editorial de las cuatro historias

- **Laberinto:** se mantienen ocho. No se agrupan todas las muertes: caída, consumo espiritual, derrumbe, devoración, locura antes de morir y resistencia fatal tienen causalidad o coste diferentes. El guardián espectral implica transformación y retención eterna; escape con secuelas conserva vida y daño mental. Devoración/resistencia podrían fusionarse solo si el autor ignora causalidad: no se hace aquí.
- **Odisea:** se mantienen seis provisionalmente. Pacto/fusión, conocimiento, renovación como viajero, rol de guardián, apertura entre realidades y lazo eterno no son automáticamente el mismo éxito espiritual. La vaguedad metafísica impide confirmar equivalencia entre fusión y lazo; se pide autor y no se comprime a tres por familia ni a uno por tono positivo.
- **Androide:** tres cierres distintos. Soborno/libertad/desmantelamiento; verdad pública/prisión; exposición/leyenda perseguida/desmantelamiento. Exponer corporación no iguala prisión y persecución. Las decisiones cosméticas que convergen en `n12` no crean desenlaces invisibles; sus contradicciones de evidencia siguen pendientes.
- **Neon:** 126 grupos conservadores, dieciocho de varios nodos y 108 individuales. Se agrupan paráfrasis con consecuencia y contexto compatibles; se separan misión completa/parcial, muerte/captura/huida, dominio/destrucción/desactivación, entrega/extracción, traición/sigilo y curación/compensación. Diez grupos de confianza baja preservan cierres problemáticos sin calificarlos como resoluciones completas. La cifra no debe usarse como premio a la fragmentación ni como medida de calidad.

## Registro persistente de descubrimientos: diseño propuesto

No se modifica `ProgressStore`, `SharedPreferences` ni la clave `mythos.progress.v1`. El código actual guarda nodo presente, historial, bandera completed y última actualización, y restart borra esa partida. Por ello no es una colección acumulativa y no permite reconstruir todos los finales históricos después de retroceder o reiniciar.

Propuesta separada: clave local **`mythos.discoveries.v1`**, sin Firebase ni dependencias nuevas requeridas. Es una sugerencia para aprobación, no una clave creada. Esquema versionado independiente:

```json
{
  "schemaVersion": 1,
  "registryVersion": "version-aprobada",
  "stories": {
    "laberinto_medianoche": {
      "discovered": {
        "escape_con_secuelas": {
          "firstDiscoveredAt": "fecha UTC ISO-8601",
          "evidenceNodeIds": ["final8"],
          "mappingVersionAtDiscovery": "version-aprobada"
        }
      }
    }
  }
}
```

La clave de cada descubrimiento es el ID semántico dentro de su historia: visitar otro terminal del mismo grupo hace **upsert idempotente**, no suma otro final. Unión sin duplicados de evidenceNodeIds conserva procedencia y la fecha más temprana válida. Los nodos originales siguen siendo evidencia, no identidad del descubrimiento. Añadir historias agrega otro namespace sin borrar los existentes; se preservan historias/IDs desconocidos o retirados para futuras versiones. Datos corruptos no justifican eliminar silenciosamente un registro: habrá que detectar, conservar respaldo y resolver el error antes de confirmar guardado.

Descubrimientos no decrecen al retroceder, reiniciar o completar otra partida. No se cambia historial ni completed para calcularlos. Conteo actual: intersección entre semánticos descubiertos y **grupos aprobados disponibles** del catálogo; archivos/IDs retirados conservados no aumentan el denominador ni se borran del registro histórico. Porcentaje = descubiertos disponibles / disponibles; tratar explícitamente catálogo vacío, no dividir por cero. Ninguno de los recuentos propuestos se incorpora todavía a biblioteca/detalle.

Registro futuro al alcanzar un terminal: resolver mapeo aprobado, escribir de forma serializada y comprobar éxito antes de confirmar persistencia a UI. Restaurar el mismo terminal reintenta idempotentemente; no duplica. Dos claves SharedPreferences independientes **no son una transacción**: entre guardar progreso y descubrimiento puede haber interrupción. La implementación deberá reintentar/reconciliar un terminal realmente restaurado y probar fallos de escritura; no prometer atomicidad por usar dos preferencias. No introducir un cambio en ProgressStore para ocultar este problema sin aprobación de fase posterior.

**Compatibilidad editorial:** el registro de grupos y el historial de mapeos tendrán versión/estado aprobado. Renombrar nodo o añadir uno equivalente conserva el semanticId mediante un mapeo explícito aprobado; no se redescubre desde texto similar, número o hash. Renombrar semanticId requiere alias aprobado antiguo → canónico. Fusionar grupos une descubrimientos y evidencia conservando fecha; dividirlos no marca automáticamente ambos hijos: mantener legado hasta contar con evidencia y autorización de asignación. Retirar un nodo o convertirlo en borrador conserva el descubrimiento semántico, aunque no cuente como disponible actualmente. Los IDs desconocidos no se descartan al cargar.

El JSON incluye `approvedMappings: []`: **no existen mapeos de compatibilidad aprobados por esta fase**. Fuente SHA-256 y versión registran qué se revisó; el hash no es identidad semántica. Todos los grupos tienen `authorApprovalRequired` y estado propuesto. Futura incorporación a assets requiere aprobación del registro y de las ambigüedades, no copiar sin más el documento.

**Partidas antiguas:** si se autoriza importar evidencia, usar únicamente IDs terminales realmente guardados y un registro compatible aprobado. No reproducir elecciones antiguas sobre conexiones nuevas ni sustituir un original por `__v2`. Historial actual no conserva todos los finales visitados tras volver/reiniciar: reconocer esta limitación y no fabricar descubrimientos. Para una importación sin fecha de descubrimiento comprobable, conservar fecha desconocida y registrar importedAt por separado, no fingir que lastUpdated es primera lectura.

**Sin spoilers en interfaz:** estadísticas públicas pueden mostrar cantidad y proporción; los grupos no descubiertos se muestran con marcador neutral si se decide mostrarlos. No renderizar nombres, descripciones ni textos de finales bloqueados, tampoco en tooltips, etiquetas semánticas de accesibilidad, búsquedas o mensajes de validación al lector. Al descubrir un grupo se permite su nombre aprobado y evidencia del final alcanzado; no revelar automáticamente los textos de otras variantes aún no visitadas. El archivo editorial sí contiene toda la evidencia porque no es una pantalla de producto.

## Duración de una partida: recomendación

Cambio de significado propuesto: **antes**, tiempo para descubrir todos los finales; **después**, lectura y decisiones desde comienzo hasta un desenlace, incluido fracaso o retirada temprana. No se estima completar todas las rutas ni se multiplica por finales. El campo real actual es **`estimatedDuration`**, entero en JSON/modelo, biblioteca y detalle; `durationMinutes` es el nombre conceptual de la solicitud, no un atributo existente que deba editarse o renombrarse ahora. No se modifican metadatos.

Recomiendo **intervalo aproximado**, porque Neon puede cerrar en tres o nueve decisiones y no se conocen preferencias de jugadores. Un escalar cabe en el modelo actual pero escondería esa variación y no sería una duración garantizada. Para respaldo escalar solo si autor lo solicita: mediana estructural del escenario intermedio, redondeada (3, 8, 1 y 3 minutos); no llamarla media de jugadores ni sumar medianas marginales.

Los siguientes intervalos orientativos combinan escenarios de 200 palabras/minuto + 8 segundos por elección y 150 + 15 de la Fase 2C; redondeo editorial, **no límites duros ni medición humana**. Android mínimo 0,895 se comunica aproximadamente como 1. El escenario contemplativo de 120 + 25 puede superar el intervalo: hay que revisar con lectores antes de publicar una promesa firme.

Al implementar intervalo, aprobar un modelo de duración versionado con mínimo/máximo aproximados y unidad “single_playthrough”, sincronizando fuente, índice e individuales mediante procedimiento existente; no cambiar solo un label dejando 120/12/50 como duración por partida.
